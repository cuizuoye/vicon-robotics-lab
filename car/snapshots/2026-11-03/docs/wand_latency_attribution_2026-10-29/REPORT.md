# Sign遥操作延迟：实测分段与优化优先级

2026-10-29。结论：本次数据支持优先优化运动能力匹配，尤其是加速度和旋转档位；不能把所有跟随滞后归咎于Vicon或网络。尚未测出“杆开始物理移动→实车轮子起转”的完整时延，本报告不把仿真结果标为实车实测。

本轮仅新增独立分析脚本、报告及10秒现有SDK统计话题的只读采样。未修改已保存的控制器/仿真入口、原演示、矩形、固件、接收器或网络设置；未打开新控制台、未启动实车。

## 1. 数据与计时边界

主要数据：[真实Sign→软件车会话](/home/PRIMARY_USER/vicon_mecanum_ws/docs/wand_fast_follow_ros_sim_2026-10-29/real_sign_5gzsjthu)。包含47.238秒ACTIVE、2356个控制周期、2345个首次使用的不同Sign同帧包，只有一个运动epoch。其末尾为Sign定位超时保护停车；轨迹拟合去掉前后各2秒，不把末尾丢失段混入响应估计。

精确使用候选中的Sign摘要、源时间戳和控制周期时间，逐一匹配完整六路原始包，重新验证原始包摘要，并与同一控制周期状态严格连接，不使用“最近的一帧”替代。重复帧只计第一次使用，不借用重复消费时的较大年龄冒充链路延迟。

ROS系统钟到本机单调钟采用每个控制周期的成对读数转换；这段两钟偏移变化范围约23.8微秒。此转换仅用于同机软件分段，不是相机曝光时钟同步。`header.stamp`来自接收器本机处理，不是曝光时间。

SDK统计使用当前既有接收器的`/vicon/latency`和`/vicon/frame_number`，没有新建DataStream连接或写参数。该10秒采样不与上次47秒手势逐帧配对，不能合成为同一次严格端到端试验。

这里的“控制周期时间戳”是进入该控制周期时的取时，不是候选发布完成时刻。缺少的耗时不能填0。六个原始回调之间的跨度中位0.349ms、P95 0.610ms，说明本次记录中齐帧本身不是主要等待。

SDK的`GetLatencyTotal()`在官方契约中是实时管线各延迟样本之和，无可用信息时可以返回0；它不包含本项目后续ROS控制、执行器、机械响应和显示链。[Vicon DataStream SDK开发指南](https://help.vicon.com/download/attachments/9437257/Vicon%20DataStream%20SDK%20Developers%20Guide.pdf)。本机SDK头文件也给出相同定义。因此不沿用工程旧注释中未经完整证明的“曝光到客户端全耗时”说法，也不将4.142ms直接加到上次会话的P95。

周期统计与时延不同：控制周期中位19.959ms/P95 25.790ms；末级门发布周期中位10.151ms/P95 15.209ms；模型反馈周期中位10.203ms/P95 17.039ms；模型快照周期中位25.511ms/P95 27.546ms。这些不能直接串行相加，多个周期并行运行。

## 3. 当前“跟不上”的主要证据

| 指标 | 结果 | 判断 |
|---|---:|---|
| 平移命令达到0.70m/s上限的时间占比 | 0% | 本组手势下，单纯提高最高速度不是首要解法 |
| 实际命令速度峰值 | 0.636m/s | 尚未达到0.70m/s上限 |
| 平移命令加速度达到0.80m/s²上限的时间占比 | 74.56% | 加速/减速/换向几乎一直受约束，优先调查 |
| 原参考领先保护保持的时间占比 | 15.59% | 部分目标还受到20cm参考领先约束；没有取消该保护 |
| 本次旋转速度许可 | 0.10rad/s，即5.73°/s | 是本次独立仿真入口的实际旧低速上限，不代表所有候选或未来实车配置 |
| 杆角速度中位/P95，100ms匹配差分 | 0.369/1.390rad/s，即21.1/79.6°/s | 远高于该旋转许可 |
| 杆角速度超过0.10rad/s的样本占比 | 77.70% | 当前配置不可能持续1:1同步旋转 |
| 旋转命令达到0.10rad/s上限的时间占比 | 30.10% | 旋转同步问题有明确的限幅证据 |
| 旋转加速度达到0.40rad/s²上限的时间占比 | 12.36% | 角加速度也会限制换向，并通过耦合整形影响组合动作 |

“达到上限”定义为不低于上限的98%，命令占比按真实控制间隔加权，杆速度占比在有效分析区间均匀采样；不把不同采样基数混算。

0.80m/s²下，从静止到0.70m/s仅理想加速就需要0.875秒；从+0.70反向到−0.70至少1.75秒。0.10rad/s下，90°旋转仅匀速部分下界就需15.71秒。这些是运动能力产生的时间，不是数据包迟到，不能靠把ROS消息加快几毫秒消除。

本次快速前馈补充分支只使用37个控制样本，停杆追赶分支使用1个样本；由于真人动作频繁换向，同向性/稳定性条件很少满足。不能把先前特定离线输入中27%～34%的位置误差改善，改写为本次真人动作的延迟改善百分比。

## 4. 仿真本身也包含人为响应环节

已保存的`Plant.step()`明确使用120ms一阶速度时间常数，并使用0.98/0.88/0.95的X/Y/yaw速度增益。这是既有近似模型，不是由本车实验辨识出来的电机参数。

仅该一阶环节对阶跃速度的理论10%→90%上升时间约263.7ms。120ms不是另一个可直接加上的纯延时，也不能通过调小模型常数就声称真车变快；下一步应保留模型不确定性，并在允许实车测量后做辨识。

速度前馈使用名义40ms的历史回归，不是把位置整体延后40ms。本次重构的实际源窗口跨度中位36.23ms、P95 39.62ms；控制周期看到的回归时间中心年龄中位29.92ms、P95 42.67ms，已经包含源数据消费年龄，不能再与11.61ms重复相加。位置低通本来就是0，不能继续通过“再取消一个位置低通”优化一个不存在的环节。

## 5. “总体延迟”目前不能压成一个固定数

在前后各去掉2秒的43.238秒有效区间，对目标和软件车使用相同50/100/200ms差分窗口：

- 整段平移最佳曲线对齐约440ms，但相关性仅0.81～0.82，低于0.90判据；**不合格，不能写成系统固定延迟440ms**。
- 7个预定义10秒、50%重叠窗口中，只有2个平移窗口符合相关性/搜索边界判据：22～32秒约430ms、32～42秒约340ms。这是局部轨迹等效滞后，不是起转延迟；不能当独立重复试验求置信区间。
- 整段旋转对齐相关性约0.47，不应给出可信的固定旋转延迟；强限幅使其更像幅值和速度不匹配，而不是同一曲线整体后移。
- 同时刻位置误差中位12.62cm、P95 33.10cm、最大57.94cm；角度误差P95约106.4°。这揭示快动作/大转角下客观同步性仍有空间，不因“仿真基本正常”的主观评价而隐藏。角度误差针对原始1:1目标，安全门约束的是受控参考，二者不是同一指标。

## 6. 优化顺序

1. **先匹配加速度与旋转档位。** 用同一段已记录Sign输入做独立、SIM ONLY对照，平移先考察加速度而不是提高最高速度；旋转要匹配实测手势角速度，并保持轮速包络和停止保护。先分开纯平移、纯旋转、组合动作，避免一改多个量。这里是证据支持的优先级，不是已经完成消融试验的因果百分比分解。
2. **明确模型贡献。** 120ms只作既有近似模型基准；速度响应辨识未完成前不以降低仿真时间常数作为真车性能成果。
3. **再压软件等待及估计陈旧度。** 10.65ms中位内部等待、25.66ms P95和70.15ms尾部值得补测源转发/DDS/调度；速度回归窗口可单独考察噪声与相位代价。保留安全门、命令有效期和来源绑定，不用扩大超时阈值“优化”同步性。
4. **最后依据同帧时间证据决定是否动Vicon输入链。** 当前SDK自报约4ms且本机六路接收约1ms，但这不等于已证明曝光/传输/SDK缓存全部无滞后。200帧缓冲容量也不等于排队200帧；没有证据前不盲改它。

## 7. 要做严格总延迟，还缺的测点

旧日志没有候选DDS发布完成、门接收/选帧校验完成、签名输出发布与模型验签接收、UI绘制提交的同序号时间戳，不能精确拆这些段。日志观察回调不能替代真实接收点，UI快照周期也不能替代屏幕呈现时间。

下一轮应建立同一记录中的`源帧/Sign摘要→控制序号→签名输出序号→模型状态序号→绘制序号`，记录每个实际边界的单调时钟，异步写日志，超出诊断缓冲容量时标记该轮无效而不阻塞控制。SDK帧号和SDK统计目前是无同帧头的独立话题，不用最近邻拼接伪造精确曝光时间。

建议先做一轮不改参数的标准化真实Sign→软件车采样：慢动作（尽量不触发限幅）、正常手持、快换向挑战、纯旋转、平移旋转叠加，每项分开且停杆保持。先获得完整分段基线，再做单因素对照。

真正的“杆物理起动→实车轮胎/车体起动”另需原来准备的同画面录像及实车条件确认。普通60fps视频可给出可见起动区间，但不足以证明10ms级改善。MCU、电机、Tenda回程和物理摩擦不能由本次软件车数据替代。
