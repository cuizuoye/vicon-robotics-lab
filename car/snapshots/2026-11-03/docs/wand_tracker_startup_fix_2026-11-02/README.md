# 浏览器启动流程修复 V1

独立入口，保留原 `start_car_tracker.sh` 和所有已冻结版本。

```bash
bash /home/PRIMARY_USER/vicon_mecanum_ws/tools/start_car_tracker_fixed.sh --launch --site-ready --operator-trial --seconds 600
```

这条启动命令仍表示操作者确认现场条件、同意受控试运行。输入命令不会自动运动：

1. 先打开常驻的“启动检查”页面。仅页面加载不会发送使能；首次连接后开始原有的失能零速握手、Vicon和门控自检。
2. 自检通过后，在**同一标签页**进入跟随界面，完成字体和世界格子的预热，再建立严格100ms操作通道。
3. 真正READY后，操作者单击空格开始；再次空格、Esc、停止按钮停车。
4. 启动失败的阶段、原因和记录位置会保留，允许操作者手动“重新检查连接”。不会自动重试。
5. 已结束的跟随页面可返回启动检查。必须旧进程退出且已确认停车，才能手动创建全新的会话；绝不恢复旧按键或旧运动授权。停车未确认时禁止重试。

无参数或 `--check` 只核对本地文件；不会连接小车。浏览器未成功打开时，终端保留完整地址。

## 变更边界

- 只改启动、呈现和提示；固定背景格子缓存，目标/车体继续实时绘制，文本刷新降为10Hz。
- 仍为1:1平移+相对旋转、600秒、0.70m/s、2.00m/s²、2.00rad/s、12.00rad/s²；无新增参考点或固定围栏。
- 主线程100ms、定位200ms、MCU反馈300ms和底层保护不变。预热不是运行期超时宽限，也不在后台伪造心跳。
- 不清硬件故障，不刷固件，不改网络，不改原矩形程序。

## 已知诊断与证据边界

历史记录含多种独立原因：失能握手RTT不合格、反馈不新鲜、浏览器回应超过100ms，以及一次MCU请求拒绝故障0x20000。它们不能一律标成UI误报，仍按原因阻断。

旧版在本次无界面Chromium的短时基线中未自发复现随机回应超时；**不能宣称已找到该随机超时的唯一根因或保证现场绝不复发**。此次修正启动期冷绘图的时序、启动失败无页面和无手动重检入口的确定性缺陷。真实浏览器故障注入、ROS和原生C固件回环测试是离线证据，不是实车验收。

`prepared_v1/QUALIFICATION.json` 为冻结离线回归；`launcher_browser/RESULT.json` 为额外的真实浏览器启动页流程验证（模拟子进程，无硬件）。本轮没有启动实车，现场新入口复验仍待完成。
