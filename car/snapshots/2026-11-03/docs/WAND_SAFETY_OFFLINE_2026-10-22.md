# 标定杆专用监督器与末级安全门：离线验收

日期：2026-10-22。本轮只完成软件仿真，不接入实车、不刷写固件，不改动已有矩形控制包。实车按用户要求继续断电。

## 实现范围

新增入口 `mecanum_wand_control/wand_safe_sim.launch.py` 固定使用 ROS_DOMAIN_ID=96、LOCALHOST 和 `/wand_safe_sim`。原域0的Vicon接收器、域99的真实Sign旧仿真，以及旧矩形入口均未切换到此新链路。

    模拟杆/带时限的使能心跳 → 专用监督器 → 候选指令 → 独立安全门
                                                               ↓
                                               签名执行通道 → 软件车

监督器与安全门为不同ROS进程，分别直接订阅原始位姿、使能租约与执行反馈，并分别检查时间、围栏和控制源。软件车另有独立命令看门狗。

新增代码：

- `safety_core.py`：无ROS依赖的监督器、独立安全门、输入校验、单调时钟及固定围栏。
- `safety_wire.py`：末级仿真执行通道签名、源身份固定、序号和有效期校验。
- `safety_nodes.py`：三个隔离ROS节点；拒绝域/命名空间/话题/服务重映射到其他路径。
- `safety_suite.py`、`safety_ros_smoke.py`：虚拟时间场景、真实ROS进程故障注入。

## 启停与恢复约定

1. 默认STANDBY，移动杆、启动launch、初始就按住使能均不会开动。
2. 必须收到新鲜的“松开”使能心跳、有效位姿、零输出和静止反馈，经过稳定窗口后，显式调用start才能进入ARMED。
3. 独立安全门确认本次新会话后，再按住使能才进入ACTIVE；此时捕获当前杆和车原点，2倍映射，保持本次车头方向。
4. 松开使能、pause或stop：丢弃旧目标，进入STOPPING。即使松开后很快又按下、两条消息发生于同一控制周期，也不能掩盖释放事件。
5. 只有新鲜执行反馈确认失能/零输出，且位姿和速度持续静止，才报告PAUSED/stop_confirmed。超过1.5秒仍无证据，保持STOP_UNCONFIRMED，而非按时间直接宣布停车。
6. 遮挡、越界等可恢复故障停稳后进入FAULT。原因消失、松开使能、显式acknowledge之后，仍须重新start和按住；新会话、新原点，不追赶旧目标。
7. ESTOP、执行器故障和运行中严重时钟/周期异常为硬锁存，不能通过acknowledge清除；本阶段须重启隔离仿真。不存在清除真实MCU故障的入口。

冷启动DDS发现期间，尚在STANDBY且从未取得运动权限的调度间隙，只会重置稳定准备窗口；不授予权限。ARMED/ACTIVE的100ms控制周期保护没有放宽。该区分经过单元测试和两轮真实ROS验收。

## 末级输出来源校验

本机Jazzy的rclpy消息回调不提供逐帧publisher_gid。联调确实验证了这一限制，因此没有把话题图里“只有一个发布者”冒充逐帧GID认证。

最终实现：

- 每次launch生成新的256位随机通道密钥，只传入该次安全门和软件车进程，不写入日志或ROS参数。
- `/wand_safe_sim/actuator_command`使用HMAC-SHA256签名；执行端核对签名、源身份、单调递增序号、单调/ROS双时基有效期及独立速度上限。
- 初始必须是有效的签名零输出；源变更、重放、过期、未来时间和篡改均拒绝。
- 普通 `/wand_safe_sim/cmd_vel` Twist仅用于观测；软件车根本不订阅它。其他程序向该话题发速度不能直接驱动车，冲突发布者也会被图检查发现并停车。
- 未经签名的伪造执行消息会使软件执行器零输出并锁存故障；删除伪造发布者不会恢复运动。

这是同一主机内的仿真通道，不是新增的ESP32/STM32协议，也不代表通过了SROS2安全认证。拥有本机同用户权限的恶意程序、密钥泄露、上游操作端认证和拒绝服务不在该防误接线/误发布机制的保证范围内。

## 验收结果

### 自动测试与构建

- 原控制包275项测试 + 标定杆包136项测试 = **411项通过**。
- `mecanum_wand_control` colcon构建通过。
- 原矩形控制包72个源文件、配置和测试文件SHA256与保留基线一致。
- STM32/ESP32及协议94个源文件SHA256与本轮开始时一致。

### 虚拟时间故障注入

`docs/wand_safety_2026-10-22_virtual_final/summary.json`中31组场景全部通过：

- 默认失能、预先按住使能、2倍斜向往返、暂停重新对齐；
- 杆/车定位丢失、冻结时间戳、使能释放/失联/重放；
- 监督器冻结、候选链路丢失、延迟/重放指令；
- 斜向合速度超限、航向超限、加速度突变；
- 抬起、倾斜、位姿跳变、车或目标越过固定围栏；
- 模式冲突、重复控制源、反馈丢失、执行器故障、急停；
- ROS时间倒退/前跳、单调时钟倒退、运行中控制周期停顿；
- 会话到时、独立末级门进程丢失。

另有单元测试覆盖签名错误、内容篡改、错误密钥、源替换、签名重放/过期/未来时间、无初始零输出、同一周期释放再按下，以及坏位姿后立刻恢复有效帧不能掩盖故障。

虚拟时间正常往返到位误差约9.59mm，重新对齐漂移0，最大合速度0.05m/s。没有模拟真实摩擦、供电、质量、无线延迟或真实制动。

### 真实ROS节点及进程故障

`docs/wand_safety_2026-10-22_ros_final/summary.json`三组综合验收全部通过，前一轮`ros_v7`也通过。它们是真实运行的ROS节点，但输入和执行器仍为软件模拟，不是实车验证。

ROS的`settled_error_m`字段在本版脚本中记录“首次进入24mm到位门限”的误差（最终一轮23.85mm），不是长时间持稳后的最终误差；不要与虚拟时间9.59mm持稳结果混淆。

这些时延是观测到控制输出或软件执行目标归零的时间，包含采样和回调开销；不是车身瞬间静止时间，更不代表实车600ms断令保护已缩短。真实制动、Tenda无线链路、物理急停、BMS/保险仍未在本阶段验证。

早期失败记录`ros_v1`至`ros_v6`保留，不当作通过证据。脚本命名冲突、Jazzy回调身份接口限制和冷启动无权限状态的调度处理已经在最终实现中修正。伪造签名场景中的日志`output signature mismatch`是预期的故障注入结果。

## 重复运行：仅仿真

    cd /home/PRIMARY_USER/vicon_mecanum_ws
    source /opt/ros/jazzy/setup.bash
    source install/setup.bash
    ros2 run mecanum_wand_control wand_safe_suite --output /tmp/wand-safe-virtual-new
    ros2 run mecanum_wand_control wand_safe_ros_smoke --output /tmp/wand-safe-ros-new

输出目录必须尚不存在。ROS脚本会自行启动、测试、退出它创建的域96三个节点；进程故障注入只针对核验为本次launch子进程的PID，不触碰已有矩形/Vicon进程。

仅打开默认待机后端：

    ros2 launch mecanum_wand_control wand_safe_sim.launch.py

服务`/wand_safe_sim/start`、`pause`、`stop`、`acknowledge`、`estop`只属于域96仿真。单独调用start并不会绕过缺失的位姿、使能心跳、静止反馈或末级握手。本轮操作端由测试脚本模拟，尚未接入真实按键/手柄或真实Sign到新安全链路的适配器；不是可直接使用的实车启动入口。
